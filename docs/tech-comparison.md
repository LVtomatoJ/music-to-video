# Beat-to-video stack comparison

## Recommendation

Use **Python (librosa + cairo + ffmpeg)** for the product.

On a 30s 1080p30 clip the Python prototype finished the render in **6.95s** (about 130 frames/s), ahead of Rust at 7.82s and the browser stack at 11.88s. Beat tracking is in the same range for all three: every stack had precision 1.0 against a synthetic 126 BPM grid, and all three locked a steady ~123 BPM on a 30s excerpt of the instrumental already in this repo. Python is the one that stays small (312 non-empty lines versus ~700) and makes the next effects ordinary functions instead of a browser driver or a rebuild. Rust is the runner-up if a single binary matters more than adding visuals. The web stack is the one to reopen for an in-browser preview, not for the export CLI.

The product in `music2video/` follows that choice: analysis, scene/effects, cairo renderer, and ffmpeg encoder are separate modules. `legacy/` keeps the original pygame demo.

## What was built

Same pipeline in three stacks: audio file in, beat/onset times out, six balls that bounce and recolor on beats, a particle burst on strong beats, MP4 with the source audio muxed back in.

| Stack | Analysis | Picture | File |
| --- | --- | --- | --- |
| Python | librosa `beat_track` + high-frequency `onset_strength` | cairo | ffmpeg libx264 CRF 20, AAC |
| Web | Chrome `decodeAudioData`, then `OfflineAudioContext` + `AnalyserNode` (smoothing 0, one spectrum per 512-sample hop) and the Ellis beat tracker | Canvas2D | WebCodecs AVC at 8 Mbps via mp4-muxer, then ffmpeg AAC mux |
| Rust | `rustfft` spectral flux + the same Ellis tracker | tiny-skia | ffmpeg libx264 CRF 20, AAC |

The test signal is generated by `tools/make_test_track.py`: 30s, 44.1 kHz, 126 BPM kick on every quarter, snare on the backbeat, eighth-note hats, a quiet bass, ghost notes, and a softer breakdown on beats 32–39. Ground truth is the kick times (63 beats) and the snare times (31 strong beats). A hit counts when it falls within 70ms. No third-party recording is used for the scored test.

Rust and the browser share that tracker on purpose, so the gap versus librosa is the library, not a straw-man peak picker. The browser really does read `AnalyserNode.getFloatFrequencyData`; it is not a Node FFT with a canvas glued on.

## Machine

Linux x86_64, 4 CPUs, Python 3.12.3, rustc 1.83.0, Node 22.14.0, ffmpeg 6.1.1, Chrome 154 (headless). Numbers below are the run saved in `docs/benchmark-results.json`.

## Results

### Synthetic track (scored)

| | Python | Rust | Web |
| --- | ---: | ---: | ---: |
| Beat F1 (70ms) | 0.984 | 0.992 | 0.992 |
| Beat precision / recall | 1.00 / 0.968 | 1.00 / 0.984 | 1.00 / 0.984 |
| Strong-beat F1 | 0.893 | 1.000 | 1.000 |
| Reported tempo | 126.05 BPM | 123.05 BPM | 123.05 BPM |
| Tempo error vs 126 | 0.05 | 2.95 | 2.95 |
| Realized grid (median gap) | 126.05 BPM | 126.05 BPM | 126.05 BPM |
| Interval CV | 0.003 | 0.020 | 0.019 |
| Analysis | 1.70s | 0.087s | 0.31s |
| Render + encode, 1920×1080×30s | **6.95s** | 7.82s | 11.88s |
| Total | 8.65s | **7.91s** | 12.20s |
| Output | 900 frames, H.264 + AAC, 4.1 MB | 900 frames, H.264 + AAC, 4.7 MB | 900 frames, H.264 + AAC, 22.9 MB |
| Non-empty source lines | **312** | 728 | 700 |

Nobody invented extra beats (precision 1.0 everywhere). Python missed the two edge beats and six quieter snares in the breakdown; the flux tracker missed only the kick at t=0 and caught every snare. The flux tracker's *reported* tempo is one autocorrelation lag off (123 instead of 126), but the beats it places are spaced at 126.05 BPM, same as librosa. librosa's grid is the tighter of the two (CV 0.003 vs 0.020).

A separate observation, not in the JSON file: the first Python analysis in this environment took **7.13s** while Numba compiled. Later processes hit the cache and land near 1.7s. Rust has no warmup. A second web render on this same machine took 17.5s, so the browser number moves around; Python stayed near 7.0s.

## Output quality

All three files are 1920×1080, 30 fps, 30.000s, 900 frames, AAC at 44.1 kHz, and the muxed audio is the test track (not silence). Circles are antialiased in cairo, tiny-skia, and Canvas2D.

Python and Rust use the same x264 settings, so their size difference (4.1 MB vs 4.7 MB) is the encoder reacting to slightly different pixels. The web file is 22.9 MB because WebCodecs was configured at 8 Mbps; CRF 20 spends about 0.6 Mbps on this flat scene. A spot check of pixel energy shows the same behavior in all three: the frame mean jumps on a beat (background flash and white rings) and the fraction of bright pixels jumps again on a strong beat (the particle burst). The larger web file is not a sharper picture of six circles.

## Code, effects, distribution

| | Python | Rust | Web |
| --- | --- | --- | --- |
| Shape | one `demo.py` | `analyze` / `scene` / `render` / `main` | page bundle + Chrome driver |
| Adding an effect | a function on the scene | a function, then `cargo build` | a function, then esbuild, then a browser |
| CLI distribution | venv + cairo + ffmpeg. librosa pulls Numba | one binary + ffmpeg | Node + Chrome + ffmpeg |
| Other delivery | a desktop window would be a different toolkit | straightforward desktop binary | the natural in-browser preview |

Scores used for the call, 1–5, weighted toward a CLI that will grow effects:

| Criterion | Weight | Python | Rust | Web |
| --- | ---: | ---: | ---: | ---: |
| Beat quality | 25 | 4 | 5 | 5 |
| Render speed of the 1080p clip | 20 | 5 | 4 | 3 |
| Output quality | 15 | 5 | 5 | 4 |
| Code size / complexity | 15 | 5 | 3 | 3 |
| Ease of adding effects | 15 | 5 | 3 | 4 |
| Ease of distribution | 10 | 3 | 5 | 2 |
| **Weighted total (out of 100)** | | **91** | **84** | **74** |

Rust takes beat quality and distribution. It does not take the render, which is what dominates a 1080p export: x264, not the language. Python takes render speed, size, and effects, and its detector is already accurate enough (F1 0.984, tempo error 0.05 BPM).

## Reproduce

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r prototypes/python/requirements.txt
python tools/make_test_track.py
python prototypes/python/demo.py \
  --input assets/test-track.wav \
  --output prototypes/out/python.mp4 \
  --beats-out prototypes/out/python-beats.json

cargo build --release --manifest-path prototypes/rust/Cargo.toml
prototypes/rust/target/release/beatballs-rust \
  --input assets/test-track.wav \
  --output prototypes/out/rust.mp4 \
  --beats-out prototypes/out/rust-beats.json

cd prototypes/web && npm ci && npm run build
node dist/drive.js \
  --input ../../assets/test-track.wav \
  --output ../out/web.mp4 \
  --beats-out ../out/web-beats.json

python tools/score_beats.py \
  --truth assets/ground-truth.json \
  --estimate prototypes/out/python-beats.json
python prototypes/benchmark.py   # rewrites docs/benchmark-results.json
```

Chrome has to be on `PATH` as `/usr/bin/google-chrome-stable` for the web driver (the path is set in `prototypes/web/src/drive.ts`).
